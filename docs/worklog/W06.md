**Bug found and fixed — generated gRPC stubs did not import.** `rag_pb2_grpc.py` contains
`from rag.v1 import rag_pb2`, because `grpc_tools.protoc` derives the dependency's import path
from the proto's declared `package rag.v1`, not from where `--python_out` actually wrote the
file. Our own service package is *also* named `rag`, so `rag.v1` does not exist at top level —
the file really lives at `rag.pb.rag.v1.rag_pb2`. Fixed with a `sys.modules` alias in a new
`rag/src/rag/pb/__init__.py`; **the generated files were not touched** (rules.md #4), and protoc
never emits `__init__.py`, so the fix survives `make proto` reruns.

**Pinned `OLLAMA_NUM_PARALLEL=4` — this was a real reproducibility hole.** ADR-017 froze the value
and `experiment-protocol.md` §1 requires it "pinned and reported per run", but it was set
*nowhere*: not in env, not in a LaunchAgent, not in the Makefile or any script — it existed only
in prose. Ollama was therefore running at its own auto-selected default, so μ_gen = 28.2 tok/s
(measured at `NUM_PARALLEL=4`) did not necessarily describe the running system. No error, just
numbers describing a different configuration — exactly the silent-failure class rules.md #1 exists
to catch. Fixed three ways: `launchctl setenv` for the session, a `RunAtLoad` LaunchAgent
(`~/Library/LaunchAgents/com.thesis.ollama-env.plist`) so it survives reboot, and `export
OLLAMA_NUM_PARALLEL := 4` in the Makefile so terminal launches are pinned even from a shell that
predates the setenv. Added `make env-check`, which `make dev` now depends on: it fails loudly if
the launchd value is not 4 and warns if Ollama is already running (Ollama reads the variable at
**start**, so a running instance keeps whatever it launched with).

**Decisions:** none needing an ADR. Three notes; the first was acted on, the other two deferred:

1. **Connection reuse to Ollama — fixed, not deferred.** `generate.py` and `embedding.py` both
   called module-level `httpx.post(...)`, opening a fresh connection per request with no
   keep-alive. Initially deferred to W7, then pulled forward for a measurement reason: **step 10
   records p50 miss latency**, and changing the HTTP client afterwards would mean the W6 number
   and the W7 probe describe different systems. Better to fix the shape before the first number
   is taken. Both now share a module-level `httpx.Client`; `embedding.py` passes `timeout` per
   request rather than on the client, because `timeout` is a per-instance pydantic field and a
   client-level default would silently ignore it.
   **Verified empirically** (throwaway harness against a stdlib keep-alive server, no Ollama):
   shared client sequential = **1 connection / 10 requests**; shared client across 4 threads =
   **4 connections / 20 requests** (one per busy thread, no errors — confirms thread safety for
   `server.py`'s `ThreadPoolExecutor(max_workers=4)`); the old per-call shape = **10 connections
   / 10 requests**.
   The **async** methods in `embedding.py` were deliberately left on their per-call
   `AsyncClient`: an `httpx.AsyncClient` binds to the event loop it is used from, so a
   module-level one is a genuine hazard — and nothing calls the async path (`retrieve.py` and
   `ingest.py` are both sync; those methods exist only to satisfy `BaseEmbedding`). Fixing what
   is used, without adding risk to what is not.
2. **Three independent concurrency limits that must agree, and currently only one is deliberate.**
   `server.py` uses `ThreadPoolExecutor(max_workers=4)`; `OLLAMA_NUM_PARALLEL=4`; W16's permit
   pool will also be 4. They coincide by accident, not design. The architectural risk is real:
   `architecture-guardrails.md` requires `admission/` to be the **sole** chokepoint, but a Python
   thread pool that also caps concurrency makes a second one, and the gateway's permit accounting
   would then not reflect where requests actually queue. **Must be resolved in W16**, and the
   thread-pool size should be justified against the permit pool rather than left at 4 by
   coincidence.
3. **Transport to Ollama is HTTP/REST and should stay that way.** Ollama exposes no gRPC endpoint,
   so changing the protocol means replacing Ollama — frozen and consumed as a black box
   (ADR-021). And the ratio makes it moot: generation is ~12 s while loopback HTTP framing is
   sub-millisecond, i.e. well under 0.1 % of the call. Note the RAG↔Ollama links are both on the
   **miss** path; the only latency-critical Ollama call is gateway→`/api/embed` on the **hit**
   path, which lands in W7 and is measured by the hit-path decomposition (proposal §9.1).

**Redis eviction:** no `maxmemory`/eviction policy set this week, deliberately. ADR-005's capacity
value is Open until W8, and ADR-017 says not to spend time tuning it for memory reasons.
`redis-stack-server` defaults to `noeviction`, so the W5 corpus index cannot be evicted by
construction — the two-region split (`interfaces.md` §D) becomes necessary only when a capacity
limit is actually set.

**Finding 2 — the run-validity gate rests on a signal whose behaviour is not characterised.**
`kern.memorystatus_vm_pressure_level` read **1 (warning)** continuously across the whole session
while the machine's state changed enormously beneath it:

| State | free+purgeable | RSS | swap used | `memorystatus_level` | `vm_pressure_level` |
| :--- | :--- | :--- | :--- | :--- | :--- |
| start | 2.45 GB | 9.6 GB | 1.53 GB | — | **1** |
| VS Code quit | 4.02 GB | 7.6 GB | 0.36 GB | — | **1** |
| after `purge` | 8.83 GB | 3.1 GB | 0.36 GB | 83 % free | **1** |
| model loaded | — | 7.8 GB | 0.36 GB | 66 % free | **1** |
| all services stopped | **0.18 GB** | — | 0.36 GB | 62 % free | **1** |

**The first reading of this was wrong and is corrected here.** It was written up as "the sensor is
stuck", on the strength of the third row — 8.83 GB free and still warning. The last row, taken
later with every service stopped, undercuts that: free pages were genuinely almost gone (0.18 GB)
and the compressor was holding **9.15 GB of data in 3.71 GB of RAM**, on a machine with **3 days
uptime** and lifetime counters of 158 M compressions / 137 M decompressions. In that state
`vm_pressure_level = 1` is **correct**, not stale.

So the two sysctls are not one-working / one-broken. They measure different things:

- `kern.memorystatus_level` ≈ percentage **reclaimable** (free + inactive + purgeable) — which is
  why it reads 62 % while only 0.18 GB is actually free.
- `vm_pressure_level` ≈ a state derived from VM health **including how hard the compressor is
  working**, not from free pages alone.

That admits a single coherent explanation the first write-up missed: the sensor may be reporting
honestly that **this machine has not been in a healthy memory state for three days** — including
at the moment `purge` artificially spiked free pages, since `purge` drops caches without reducing
the compressor's workload. The competing explanation (a stale notification level) is still live.
Both remain open; the observation that it never once read `0` is the only firm fact.

**Discriminating test, to run before the ADR: reboot, then read it with nothing loaded.** Reads
`0` → the sensor works, and the real finding is that *measured runs need a rebooted machine*, a
protocol step, not a new signal. Still reads `1` with ~12 GB free on a fresh boot → it is broken
and must be replaced. The two outcomes produce materially different ADRs, so the ADR waits.

What holds either way, and is worth adopting regardless: **swap delta measured across the run**
(`Swapins`/`Swapouts` from `vm_stat`, before and after) asserted to be zero. "Green pressure" was
always a proxy for "did not swap"; measuring the swap directly tests the actual thing and is
verifiable *after* the run rather than requiring a ritual before it. This session's generation
left swap flat at 363.94 MB — the honest evidence that nothing swapped. Model residency confirms
the headroom: `qwen3.5:2b-q4_K_M` 1.70 GB + `nomic-embed-text` 0.37 GB ≈ 2.1 GB, `context_length`
8192 as frozen.

This matters well beyond W6: `CLAUDE.md` and proposal §7 make this sysctl the signal that decides
whether a run is **valid**, and **W8's μ_hit probe is gated on it.** Reading `1` when it should
be `0` blocks everything — safe. Reading `0` when it should not is the silent-failure direction,
and nothing in this session tested that direction.

This run was therefore taken **outside `make dev`**, whose guard correctly still refuses. The
guard was deliberately **not** weakened to let it through — it keeps blocking until the question
above is settled, which is the right behaviour for it to have.

**Finding 3 — `latency_ms` cannot express a hit, and W8 needs it to.** `handler.go` computes
`time.Since(start).Milliseconds()`, which truncates to integer ms, so every Tier-1 hit reports
**`latency_ms: 0`** — measured true cost is ~0.6 ms. W8's exit criterion is "**μ_hit recorded**",
and μ_hit is a *rate*: `1 / hit_latency`. From a field that is always 0 it is not merely
imprecise, it is undefined. `latency_ms` is frozen in `interfaces.md` §A so the wire field should
not change on a whim; the likely resolution is to measure μ_hit server-side out-of-band (as the
§H evaluation log will do from W9) rather than from the client-facing field. **Decide before the
W8 probe, not during it.**

**Plan deviation — the Redis two-region split (step 9) is not implementable as written.**
`maxmemory-policy` is **server-global, not per logical DB**, so `interfaces.md` §D's "logical DB"
option cannot produce two policies inside one instance. Separately the study's capacity is
`round(0.25 × K)` **entries** (ADR-027) while Redis `maxmemory` is a **byte** budget, so
Redis-native LRU cannot express the bounded cache at all — capacity has to be enforced in Go.
Shipped `make redis-check` instead, asserting the only currently-correct configuration
(`maxmemory-policy=noeviction`, `maxmemory=0` — nothing evictable, so no `dep:*` and no
`corpus:*` can be lost). `make dev` depends on it, so it runs before every local run instead of
being a one-time setup belief. Both this and finding 2 fold into one ADR before **W9**, when
`deps/` turns "safe by default" into a load-bearing guarantee.

Tier-2 does not exist yet) — must land before any purge path is measured. And Tier-2 itself is

**Finding that outranks everything else in this task — `OLLAMA_NUM_PARALLEL=4` is not in effect,
and cannot be.** Neither reviewer found it; it came out of reading the Ollama server log from the
exit-test run:

```
llama-server ... -c 8192 -np 1            <- effective parallelism 1, not 4
llama_context: n_seq_max = 1
srv load_model: initializing, n_slots = 1, n_ctx_slot = 8192
WARN sched.go:509 "model architecture does not currently
     support parallel requests" architecture=qwen35
```

Ollama accepts the variable, echoes `OLLAMA_NUM_PARALLEL:4` back in its own `server config` line,
then **overrides it to `-np 1`** because Qwen 3.5's architecture does not support parallel
requests in Ollama 0.33.2.

This is not new. `~/.ollama/logs/server-{3,4,5}.log` (2026-08-15 / 08-16 — the W5 spike that
produced **ADR-017 and ADR-021**) show `-np 1` in every instance, three occurrences each, never
`-np 4`. Model blob `sha256-7a3a8d553821` in those logs is the same blob loaded today for
`qwen3.5:2b-q4_K_M`. Same model, same single slot, then and now. At spike time the variable was
additionally pinned nowhere at all, so Ollama was picking its own default — also 1.

Every check passes while this is false: `make env-check` → `launchd=4`; Ollama's own config line
→ `OLLAMA_NUM_PARALLEL:4`; a run manifest per `experiment-protocol.md` §1 → reports 4. The model
serves on one slot. **ADR-017's μ_gen ≈ 28.2 tok/s is a one-slot number recorded as a four-slot
aggregate**, and the permit pool — specified as `OLLAMA_NUM_PARALLEL + headroom`, the core
parameter of the 60 %-weighted contribution — would be sized to 4 against a 1-slot backend,
putting the queue behind Ollama where the gateway's permit accounting cannot see it.

**W6's own numbers survive this.** Both recorded latencies were measured one request at a time,
and sequential latency does not depend on slot count. What it reaches is μ_gen, λ_max and
Headline A — i.e. W8 onward, not W6.
