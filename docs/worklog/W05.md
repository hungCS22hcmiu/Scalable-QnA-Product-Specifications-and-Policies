### 2026-08-15  ·  3 hours

**Did:** Ran the W5 feasibility spike against the machine's real memory constraint (other projects
keep it to ~9–10 GB used / ~5–6 GB free, not a dedicated 16 GB envelope). Gemma 4 E2B (smallest
Gemma 4 variant, smallest quant) entered yellow pressure at the lightest possible config (7.7 GB
resident, `num_ctx=4096`, `NUM_PARALLEL=1`) — triggered ADR-017's escalation clause. Empirically
compared 5 replacement candidates (memory footprint across `num_ctx∈{4096,8192}×NUM_PARALLEL∈{1,4}`
plus 5 structured RAG-QA test questions each): Gemma 3 1B (1.2–1.3 GB, 4/5 QA), Gemma 3 4B
(4.3–5.0 GB, 5/5), Qwen3 4B (3.5–5.3 GB, 5/5), Qwen2.5 3B (2.4–3.1 GB, 5/5), Qwen3.5 2B
(1.6–1.7 GB, 5/5 — smallest footprint of the 5/5 group). Chose Qwen3.5 2B. Hit an HTTP 500 on every
request under Ollama 0.22.1 (architecture too new); upgraded to 0.32.13, which fixed it. Found the
model defaults to a hidden thinking mode that inflates latency ~5x for no quality benefit — fixed
with `think: false`. Froze the largest holding-green cell (`num_ctx=8192`, `NUM_PARALLEL=4`,
1.7 GB, μ_gen ≈ 28.2 tok/s aggregate).

**Decisions:** ADR-021 (Qwen 3.5 2B replaces Gemma 4 E4B, supersedes ADR-002) — new. ADR-017
flipped from Open to Decided, frozen at `num_ctx=8192, NUM_PARALLEL=4`.

**Blockers:** none blocking — the original model choice (ADR-002) turned out not to fit the real
hardware constraint, resolved via ADR-017's own pre-written escalation path.

**Exit test:** not attempted — this entry covers spike gate 1 only (`/spike` → freeze ADR-017,
record μ_gen: **done**). Gate 2 (ADR-003 embedding model, ADR-014 chunking) and the `dev-v0`
build/ingest/retrieval exit test are still open.

**Next:** freeze ADR-003 (embedding model) and ADR-014 (chunking config) — both block ingestion.

### 2026-08-16  ·  1 hours — `/gate` run

**Did:** Ran `/gate` for real (not self-reported). Decomposed the W5 Done-when into 5 checks: memory
budget published (PASS, no `TODO(spike)` left), μ_gen recorded (PASS, 28.2 tok/s, not a
placeholder), envelope frozen-from-measurement process (PASS, ADR-017 documents real multi-trial
green readings), **envelope currently holding green — live re-check (FAIL)**, `rag ask` returns
chunk IDs for 10 fresh live queries (PASS, 10/10).

**Live regression found:** loading the frozen model (`qwen3.5:2b-q4_K_M`, `num_ctx=8192`) just now
reads `kern.memorystatus_vm_pressure_level=2` (yellow), sustained after 5s settle — not the green
recorded in ADR-017. Root cause: total RSS across all processes right now is ~12.4 GB, not the
~9-10 GB "other apps" ceiling the spike's readings assumed — more VS Code windows, browser tabs,
Zalo, and Claude sessions are open than during the original test. **The frozen config
(`num_ctx=8192, NUM_PARALLEL=4`) is not wrong — it's conditional on the operating discipline being
held, and that discipline is not currently being held.**

**Decisions:** none — no ADR needed; this is an operating-discipline lapse, not a frozen-value
problem.

**Blockers:** none blocking W6 start, but flagged below.

**Exit test:** **PASS on the 4 literal criteria** (budget published, μ_gen recorded, envelope
frozen-from-measurement, `rag ask` returns chunk IDs ×10) — **plus one live-only finding**: green
pressure does not currently hold under today's actual app load. Not a gate failure for W5's own
scope (the measurement/freezing task was done correctly, with real evidence), but a real risk
carried into W6, which adds gateway + generation + retrieval running together — strictly more
memory pressure than the retrieval-only path just tested.

**Next:** before/at the start of W6 — close the machine back down to the ~9-10 GB "other apps"
ceiling (extra VS Code windows, browser tabs, Zalo, redundant Claude sessions) and re-check
`kern.memorystatus_vm_pressure_level` holds green with the model loaded, **before** adding the
gateway's own memory footprint on top. If it still doesn't hold green even at the disciplined
ceiling, ADR-017 needs revisiting before W6 proceeds.
