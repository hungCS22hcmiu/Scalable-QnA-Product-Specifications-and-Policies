## 1. Done since 16 Oct

### 1.1 Phase 3: the `v1` corpus and workload (closed 23 Oct)

**The corpus: 164 documents, 539 chunks.**
- **152 product documents from Amazon-PQA** (491 chunks). Six PQA product categories are mapped onto four
  store departments: phones, laptops, electronics and furniture (ADR-002). The products were drawn by one
  rule fixed before the draw (ADR-011).
- **12 policy documents** (48 chunks), written by us, because PQA has no store policies. They follow rules
  fixed before the text (ADR-012). **Each condition has its own document**: returns for opened and for
  unopened phones are two files, and so are new and renewed laptops, and domestic and international phone
  warranty. This is the only defence against "same evidence, opposite condition" traps (§3).
- **Redistribution of Amazon-PQA is not granted.** The repository ships a build script and hash manifests,
  never the corpus text.

**The workload: 1,274 questions**, written under rules fixed before the text (ADR-013). It is split **by
seed-question cluster**, so a question and its paraphrases never sit on both sides of the split. Every
question is tagged with one stratum:

| Stratum | Meaning | Validation | Test |
| :--- | :--- | ---: | ---: |
| A | similar wording, same evidence: safe to reuse | 371 | 390 |
| B-within | similar wording, different evidence, **same product**: a trap | 124 | 148 |
| B-cross | similar wording, different evidence, different product: a trap | 11 | 11 |
| C | different wording, same evidence: needs Tier 2 | 83 | 67 |
| D | grounds in a product **and** a policy | 33 | 36 |
| | **total** | **622** | **652** |

**The corpus gate (G1 to G5) checks that the corpus contains the effect the study needs**, before it is
frozen. **G1 failed:** it needs at least 50 pairs with high similarity but different evidence, and `v1` has 21.
The author chose to freeze `v1` anyway and record G1 as a **finding that limits C1**, not to change the gate
(ADR-014, ADR-015). The other four criteria pass.

### 1.2 Phase 4: invalidation (closed 29 Oct)

- **The MIXED lane is decided** (ADR-016). Questions about a product *and* a policy (stratum D) get one pinned
  band, run as an on/off arm and never swept. Every log record names the arm.
- **A dependency map with blind purge** (item 4.1). Each cached answer is registered under the chunks it was
  built from. When a chunk is edited, every answer that used it is removed from both tiers. The read path
  checks a lock-free (copy-on-write) set of removed entries.
- **An epoch guard on write-back** (item 4.2, ADR-008). If a source changes while an answer is being
  generated, that answer is thrown away instead of being written back after the purge.
- **Every Tier-1 key of an entry is tracked** (item 4.3), so eviction and purge never leave a copy behind.
- **The edit path and the update set** (item 4.4). An edit reaches the gateway through `POST /invalidate`.
  The update set has 20 edits on `v1`: 10 *substantive* (they change an answer) and 10 *cosmetic*, half on
  policies and half on products.

**Functional results** (`v1`, not citable):
- each of the 10 policy edits had 4 to 11 dependent answers, and all of them were removed from both tiers;
- an edit that landed during a generation discarded that write-back;
- **completeness was 1** (no stale answer survived), and **precision was 0.695** (some removed answers did
  not depend on the changed fact).

These are the numbers RQ3 will measure properly in Phase 6 (§4.2).

### 1.3 Bugs found and fixed

1. **Redis indexes could disappear during tests** (fixed 29 Oct). The Go tests used the live Redis server, and
   their database flush also dropped the search indexes. They now run on their own server, and the gateway
   waits until its cache index is fully built. A run with any Tier-2 search error is now invalid (run rule 12).
2. **The model server kept every prompt in memory** (fixed 29 Oct, ADR-017). This was the important one.
   - **The cause.** Ollama 0.33.2 starts its runner with an 8 GB prompt cache. Our prompts almost never share
     a start, so the cache grew by about 82 MB per request and reused nothing.
     - **Measured:** the runner grew from 3.1 GB to 7.1 GB over 50 requests, and memory pressure turned
       yellow.
     - **It was hidden:** the usual memory figure (RSS) stayed near 2.3 GB.
   - **A second hidden cache.** It could also skip most of the work for a repeated question, which would have
     made the "no cache" baseline look faster than it is.
   - **Both are turned off**, through Ollama's environment (`make ollama-env`, needed after every reboot).
     `make env-check` now fails if either is on.
   - **After the fix:** memory stayed flat over 300 requests (+1 MB, in two separate runs), and speed did not
     change: about 480 tokens/s to read a prompt and 34 tokens/s to write.
   - **A correction.** The "1.7 GB resident" figure in the proposal was Ollama's own estimate. The measured
     footprint is about **3.0 to 3.1 GB** at load, and 855 MB of that is a vision encoder we cannot switch
     off. The envelope still fits the machine.
3. **Two live checks still used the old corpus** (fixed 29 Oct). The check that text crosses the Go/Python
   boundary in the right order, and the check of the support gate on live text, now run on `v1`. A new check
   also stops the support test from passing when the product is missing from the retrieval.

## 2. The system today

### 2.1 Architecture

| Part | What it does |
| :--- | :--- |
| **Go gateway** | Receives every question; runs both cache tiers and the reuse rule; admission control; coalescing of identical questions; the dependency map and purge; one log record per request |
| **Python RAG service** | Ingestion, chunking and embedding; retrieval, optionally limited to one product; calls the model on a miss. It talks to the gateway over gRPC |
| **Ollama** (on the host) | Qwen 3.5 2B (4-bit) for answers, `nomic-embed-text` for vectors. One answer at a time |
| **Redis** | The corpus vectors, both cache tiers, the eviction order and the dependency records. It holds only copies: the corpus of record is the JSON files |

**The life of a request, in one line.** Tier 1 (same words, same product) → Tier 2 (embed the question and
retrieve evidence **at the same time**, then the reuse rule) → on a miss: wait for the generation slot →
generate → write back to both tiers and register the dependencies.

The detailed pipelines are in `docs/1-System Docs/Pipelines/`:
- **Corpus** and **Workload:** raw PQA files → selection → cleaning → JSON documents → the workload and its split;
- **RAG:** chunking, embedding, scoped retrieval;
- **LLM**, the **whole request**, and **write-back**.

### 2.2 Admission control

- **The machine serves one generation at a time.** Ollama runs this model on one slot, whatever is
  requested (ADR-003). So the gateway grants **one permit**, with a small waiting queue.
- **Overload is visible.** When the queue is full, the gateway answers `503 busy, retry`. A request is never
  left to wait invisibly inside Ollama.
- **Admission control protects capacity; it does not raise it.** The cache raises capacity, by turning slow
  generations into fast lookups. Admission control keeps goodput and latency bounded **past** saturation,
  where an uncontrolled system would queue and slow down. Item 7.5 now measures both cases.
- **Memory is fixed when the model loads**, about 3.0 to 3.1 GB for the answer model (§1.3). Admitting
  requests adds none, now that the prompt cache is off. Runs are valid only while macOS memory pressure is
  green.

### 2.3 Invalidation

Every answer is registered under the chunks it was built from. An edit purges all of them, which is
"blind" purge: it is complete by design and pays for it in precision. The epoch guard closes the race with an
answer generated during the edit. Three rules keep this silent-failure-free:
- dependency records are never evicted;
- every Tier-2 entry carries its Tier-1 key;
- write-back is guarded by the epoch.

## 3. Tier 2: what we learned

Full detail: `docs/1-System Docs/Tier 2.md` (§8 and §12a).

### 3.1 The overlap check was dropped from the served rule (ADR-019)

**The proposal's rule had four checks:** similarity, namespace, **source overlap θ**, and the support gate.
The served rule uses three. Retrieval is limited to the product in question, and a product has about 3.2
chunks. So two questions about the same product retrieve almost the same chunks, whatever they ask.

**Measured** on the `v1` validation split (416 pairs, not citable):

| Pairs | Mean overlap | Overlap ≥ 0.6 |
| :--- | ---: | ---: |
| paraphrases (should reuse) | 0.876 | 86 % |
| same-product traps (should not reuse) | 0.784 | 85 % |
| other-product traps | 0.000 | 0 % |

**No threshold θ separates the first two rows**, and the third is already separated by the namespace. So θ
is computed and logged as a counterfactual, never used to decide, and not swept. This is also a small
finding: **under product-scoped retrieval, evidence overlap carries little more than product identity.**
GroundedCache's overlap gate would behave the same way in this setting.

**Consequences:**
- **Two traps, two mechanisms.** On traps across products, the **namespace** does the work. On traps inside
  one product, only the **support gate** can refuse, and that gate is adopted from GroundedCache, not claimed.
- **The baseline.** Configuration 3 is now defined as **similarity alone**, GPTCache's rule. The ladder
  3 → 4 (gate off) → 4 (gate on) shows the share of the namespace and the share of the gate separately.

### 3.2 Every known trap

`Tier 2.md` §12a lists 12 kinds of false hit and 10 kinds of false miss, with the check that stops each one
and when it still gets through. Three need the supervisor's attention, because the frozen workload hardly
contains them:

1. **The condition said in other words.** The opened and unopened policies are separate documents, so the
   right one must be ranked first for the namespace to protect the answer.
   - With the condition word in the question, retrieval ranks the right document first for 98 of 121
     questions (81 %).
   - With a synonym ("still sealed", "used", "factory-sealed"), it does so for only **24 of 43 (56 %)**, and it
     tends to pick **the opposite condition**. The embedding follows the letters ("never opened" contains
     "opened").
   - This is a **retrieval** limit: even with no cache, the model would answer from the wrong policy.
2. **Same evidence, opposite condition** ("removable?" against "not removable?"). No check can see it. It is
   reported as RQ2a, with its own interval.
3. **Tier-1 normalisation collisions.** Removing punctuation merges "1.5 m" with "15 m", and "-10 °C" with
   "10 °C". No `v1` question collides (gate G3), so no number is affected, but a real deployment would need a
   better normaliser.

None of these is fixed now: the corpus, the workload and the retriever are frozen. They are reported as
limits (§5).

## 4. How the contributions will be measured

Every threshold is chosen on the **validation** split and reported on the **test** split. Every rate carries
a Wilson interval. A result that does not support the claim is reported as it is.

### 4.1 Headline B: the reuse rule (Phase 6)

**Five configurations, on identical workloads:**
1. no cache;
2. Tier 1 only;
3. similarity alone, with τ swept: the state of practice;
4. the served rule, in three arms: gate off; gate on; gate on with the MIXED lane;
5. the full system.

**The headline figure** plots hit rate against false-hit rate, for configuration 3's τ sweep against
configuration 4. The comparison is made **at the false-hit budget δ ≤ 5 %**.

**Reported beside it:**
- **results per stratum**, with B-within apart from B-cross;
- **a static-cache control:** every configuration judged on the same frozen cache state;
- **RQ2a:** the residual of same-evidence traps;
- **decisions changed by provenance:** how often the rule disagrees with similarity alone;
- **hit-path latency**, because the rule costs a retrieval round-trip.

### 4.2 RQ3: invalidation (Phase 6, item 6.5)

Runs **with source edits during the run**:
- **stale-answer rate**: configuration 3 (no dependency-aware purge) against configuration 5;
- **completeness and precision**, split into substantive and cosmetic edits;
- **false hits by cause**, so a stale answer is never blamed on the reuse rule;
- **a swept TTL baseline**: the whole staleness/hit-rate curve that TTL expiry can reach, with blind purge as
  one point against it.

Item 7.4 adds the read path's p99 latency while purges fire under load.

### 4.3 Headline A: capacity (Phase 7)

**Scalability here means sustainable request rate on one fixed machine**, not the number of questions and
not scale-out. **Questions repeat in real traffic**, so query popularity follows a Zipf distribution, swept
over three levels. A run can be thousands of requests long, drawn from the 652 test questions; the cache
holds only 0.25 × K entries, so eviction is real. More distinct questions would not change what is measured.

| Measured | Shows |
| :--- | :--- |
| Goodput and p50/p95/p99 latency against offered load, for configurations 1 → 2 → 5, at each Zipf level | How much each tier raises sustainable load |
| μ_gen (the generation rate) and μ_hit (the rate when every request hits) | The two terms of the capacity model; the crossover h\* is computed from them |
| Measured λ_max against the model | Whether the model predicts what the machine does |
| Shed rate, queue depth, goodput and p99 with and without admission control | That overload is shed explicitly and goodput does not collapse |
| Memory footprint and pressure over time | That memory stays flat and green |

**Two figures give a sense of scale:**
- **Without the cache**, one generation takes about 2.8 s, so the machine serves about 0.35 questions per
  second.
- **A cache hit** costs milliseconds. Earlier probes on `dev-v0` gave about 8,000 req/s for Tier 1 and about
  60 req/s for Tier 2: planning figures only.

The load generator runs on the same machine (there is no second machine), so every capacity figure is a
**lower bound** (ADR-001).

### 4.4 Phase 5 comes first

Phase 6 needs a trustworthy label: "was this reuse a false hit?" Phase 5 builds it.
- **P1:** the metric definitions, counting rules and run record.
- **The judge:** a model different from the generator, with a frozen prompt, run offline.
- **Agreement:** with human labels, and between two labelling schemes (with and without a reference answer).
- **δ:** finalised above the judge's own measured error.
- **The figure pipeline:** every figure regenerates from raw logs.

## 5. Limitations and threats to validity

- **One machine, one model, one corpus.** No result is claimed beyond this envelope.
- **Co-hosted load generation.** Capacity figures are lower bounds. Latency at high load is indicative only.
- **G1 failed** (21 trap pairs against 50). The power to show C1 on same-product traps is limited.
- **The workload is LLM-written and mostly literal.** It rarely says a condition in other words. False hits
  from synonyms and from Tier-1 normalisation will be understated (§3.2).
- **Labels inherit retrieval errors.** The reference answer is generated from the system's own retrieval.
  Item 5.2's labelling ablation measures how much this matters.
- **The support gate is strict.** About one right answer in ten is refused against its own evidence
  (`dev-v0` sample). That costs hit rate, not safety.
- **Product scoping makes overlap uninformative** (ADR-019). It is stated as part of the claim, not hidden.

## Questions for the supervisor

   restatement:

   > **within the same grounding namespace** (product or policy document, with a lane for questions that
   > ground in both) **and** the freshly retrieved evidence still supports the cached answer, sustains more
